어느 날 보험사의 메시징 시스템에 장애가 발생했다.

MQ 컨슈머 쓰레드들이 모두 OOM으로 종료되었다.  
그 결과 브로커에는 메시지가 계속 쌓였고, 어느 순간 Pending 메시지가 20만 건까지 증가했다.
결국 브로커 또한 OOM으로 비정상 동작하기 시작했다.

장애 원인을 분석해보니 ActiveMQ Prefetch 설정이 핵심 원인이었다.

### ActiveMQ Prefetch 란 무엇인가?
ActiveMQ는 기본적으로 Push 방식을 사용한다.
즉, 브로커가 컨슈머에게 메시지를 보내주는 구조이다.

> Kafka 의 경우 Pull 방식이며, 이 방식은 컨슈머가 브로커에게 요청해서 받아가는 것을 의미한다.

Push 방식에서는 브로커가 메시지를 컨슈머에게 계속 밀어넣을 수 있게 된다.  
하지만 이렇게 되면 컨슈머가 처리 가능한 양보다 많은 메시지를 받게 될 수도 있다.  

(컨슈머 메모리가 초과되거나, 다른 컨슈머가 유휴 상태인데도 지연상태인 컨슈머한테 다 몰려있거나)

그래서 이 문제를 해결하기 위해 존재하는 설정이 Prefetch 이다.  
Prefetch는 브로커가 컨슈머에게 미리 내려줄 메시지 건수를 의미한다.

### 그러면 그게 왜 필요한 것인가?
브로커와 컨슈머는 같은 서버에 있을 수도 있지만, 다른 서버에 있을 수도 있다.  

만약 다른 서버에 있다고 한다면, 메시지를 받아오는 과정에서 반복적인 네트워크 I/O 비용이 발생한다.  
따라서, 성능을 높이기 위해 ActiveMQ는 브로커가 한번에 메시지를 내려주고 컨슈머가 메모리에 쌓아두고 하나씩 처리하게 한다.  

### 그러면 그게 왜 장애가 되었는가?

#### 거대한 메일 본문 사이즈
어느날 보험사에서 자동이체 안내 메일을 보내게 되었고, 이 달은 평소보다 많은 건수를 보내 100만건을 보내게 되었다.  
보안모듈까지 씌워진 메일 본문은 500KB 정도를 차지하므로 메일 사이즈 또한 평소보다 컸다.  

#### SMTP 속도 제한
그리고 많은 건수를 보낸다고 해도, SMTP 발송은 수신서버의 제한사항이 존재해 무한히 빠르게 보낼 수 없다.  
그래서 IP 당 한 시간에 10 - 15 만건 정도가 현실적인 발송 속도가 된다.

#### Prefetch
ActiveMQ Queue의 Prefetch 기본 값은 1000으로 설정되어 있다.  
즉, 브로커는 컨슈머에게 1000개의 메시지를 한번에 내려줄 수 있다.  

문제는 메세지 크기였는데,
- 메시지 크기 : 500KB
- Prefetch : 1000

이러면 컨슈머 하나가 메모리에 500MB 정도의 데이터를 들고 있을 수 있게 된다.  
하지만, 해당 모듈의 힙 사이즈는 2GB로 4개의 컨슈머 인스턴스 Prefetch 버퍼가 가득 차면 OOM이 발생할 수 있는 구조였다.

실제 장애 상황에서도,
1. 브로커가 Prefetch 1000개 씩 컨슈머에게 전달
2. 컨슈머 메모리 사용량 증가
3. 컨슈머 힙 메모리 고갈
4. 컨슈머 OOM 현상 발생 및 컨슘 중단
5. 브로커 Pending 폭증
6. 브로커 메모리 압박으로 Producer 블로킹 처리

다음 단계에 따라 연쇄적으로 발생하면서, 다른 모듈간의 연계도 모두 불안정해지는 상태가 되었다.

### 그러면 어떻게 개선했는가?
#### Producer 단계의 RateLimiter 적용

먼저 Producer 의 발행 속도를 제어했다.  
일단 브로커에 메모리가 과도하게 쌓이는 걸 막고, 컨슈머 TPS 만큼의 발행 속도를 유지하려고 했다.

브로커의 Pending 기준으로 동적으로 발행 속도를 조절하는 방식도 고려했으나, 현실적으로 아래와 같은 이유로 진행하지 않았다.  
- Pending 이 과도하게 유지되어 발행이 멈춰지는 경우, 배치 잡이 종료되지 않아 DB 커넥션 장기 점유 위험성
- 내부 시스템 상 1차 큐 -> 2차 큐로 옮겨지는 형태이므로 Pending 카운트 주체 모호

따라서 당시에는 TPS 설정 값 입력을 통한 RateLimiter 방식을 활용했다.  
구현은 Guava의 RateLimiter 을 사용했고, 코드상으로 간략하게 보면 아래와 같다.  
```java
private RateLimiter emailSendQueLimiter = RateLimiter.create(maxTPS); // 설정 상 TPS 값

public void sendMessage(String queueName, Object model) throws JMSException {
    emailSendQueLimiter.acquire();
    
    // ActiveMQ 발행 로직
}
```

#### ActiveMQ Prefetch 조정
Prefetch 조정은 Trade-Off 가 존재한다.
- 낮출수록 => 네트워크 I/O 증가, 메모리 사용량 감소
- 높일수록 => 네트워크 I/O 감소, 메모리 사용량 증가

이 상황에서 나는 Prefetch 를 1000에서 10으로 조정하기로 결심했고, 이유는 아래와 같았다.  

- 컨슈머간의 부하분산  
  ActiveMQ의 Prefetch 로 내려간 메시지는 컨슈머의 ACK 가 오거나 컨슈머가 중단되기 전까지는 다른 컨슈머에게 전달되지 않는다.  

  따라서, 다른 컨슈머가 유휴 상태일지라도 특정 컨슈머에게 전달된 메시지는 다른 컨슈머가 처리할 수 없으므로 컨슈머간 부하 분산이 원활하지 않게 된다.  
  이 값을 낮춤으로써 유휴 컨슈머도 더 많은 메시지를 처리하게 해 부하를 전체적으로 분산할 수 있을 것이라고 판단했다.  

  

- 메모리 사용량 감소 및 네트워크의 물리적 거리  
  이번 이슈가 메모리 과도 사용으로 인한 것이므로, 메모리 사용량을 줄이는게 최우선 항목이었다.  
  증가하는 네트워크 I/O 의 경우에는 DMZ 와 AP 서버는 동일 IDC 내부 네트워크에 위치해 Latency 가 매우 낮은 환경이었다.   
  따라서 메시지를 가져오는 네트워크 I/O 가 전체 처리 성능에 큰 영향을 미치지 않을 것이라고 판단했다.

#### 결론
이후 동일 환경에서 300만 건 이상의 이메일을 발송하는 이벤트가 있었지만, Prefetch 조정 이후에는 장애 없이 안정적으로 처리할 수 있었다.
